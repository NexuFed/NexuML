**Goal:** persist observations from a working scenario. **Prerequisites:** installed
NexuML, writable destinations, and any optional logger dependencies/service credentials.
Assign the examples to `ScenarioSpec.logging`; services remain backend-owned.

## TensorBoard

TensorBoard support is part of core:

```python
from nexuml.core.types import LoggingSpec, TensorBoardSpec

logging = LoggingSpec(
    experiment_name="MyProject",
    tensorboard=TensorBoardSpec(log_dir=".experiments/tensorboard"),
)
```

Train the scenario, then inspect the configured directory:

```bash
nexuml train my-scenario
tensorboard --logdir .experiments/tensorboard
```

Use the resolved directory instead if `NEXUML_LOGS_ROOT` is set. Expect event files and
actual emitted curves, not every possible metric. The terminal service summary identifies
the selected logger/paths. Stop the TensorBoard server with Ctrl-C when done.

## MLflow

```bash
uv pip install "nexuml[tracking]"
```

```python
from nexuml.core.types import LoggingSpec, MLflowSpec

logging = LoggingSpec(
    experiment_name="MyProject",
    run_name="baseline",
    mlflow=MLflowSpec(
        tracking_uri="sqlite:///.experiments/mlflow.db",
        experiment_name="MyProject",
        log_model=False,
    ),
)
```

After training, inspect the configured store/service for the actual run. HTTP tracking
URIs are passed through; credentials and service deployment are external to NexuML.
Do not persist secrets in scenarios. `log_model=False` does not request MLflow model logging;
use the [NexuML package export](/how-to/export/) when you need a portable artifact.

### Local SQLite metadata, S3 artifacts

Keep SQLite on the worker's local filesystem; S3 is the artifact store, not a
live SQLite filesystem. Configure both destinations explicitly:

```yaml
logging:
  mlflow:
    tracking_uri: sqlite:////approved/run/logs/mlflow.db
    artifact_location: s3://rglitza/logs/my-unique-run
    experiment_name: my-unique-run
    auto_nested_runs: false
    log_model: false
```

For the IKA S3-compatible endpoint, the worker and any later artifact reader need
`MLFLOW_S3_ENDPOINT_URL=https://s3.ika.rub.de`, `AWS_CA_BUNDLE` pointing to the
approved CA bundle, and the storage's approved authentication configuration.
Keep credentials out of scenario files and use the standard AWS provider chain.
Do not disable TLS verification. Install the `tracking` and `s3` extras in the
prepared environment; the endpoint is independent of the SQLite tracking URI.

Use a fresh experiment/database for a changed artifact location: an existing
experiment retains its original artifact root. Preserve existing stores rather
than deleting them to redirect new runs. Retain the local database after writers
finish so the metadata can be reopened; putting artifacts in S3 does not back up
the SQLite database automatically.

The fixed Physical AI acceptance cases use a private SQLite database per attempt
and distinct `s3://rglitza/logs/physical-ai/` artifact prefixes, then download and
validate the produced media through MLflow. Their intentional **local destination
obstruction** negative case stays local to prove partial-delivery failure; it is
not an S3 availability test or an alternative normal artifact store.

## DVCLive

Install `dvclive` in the consuming environment, then use:

```python
from nexuml.core.types import DVCLiveSpec, LoggingSpec

logging = LoggingSpec(dvclive=DVCLiveSpec(dir=".experiments/dvclive"))
```

Inspect that directory after the run for actual DVCLive outputs.

## Requested tracking failures

An explicitly selected backend is required, not best-effort. Missing dependencies,
invalid destinations and initialization errors fail the run with the backend and
original diagnostic, including requested MLflow system metrics. This applies to
supervised/reinforcement sessions and standalone evaluation.

If a later backend fails initialization, previous loggers are finalized as failed.
A newly created MLflow child is marked failed if its Lightning logger cannot start;
a supplied existing run is not terminated by that construction failure. Cleanup
retains the original error and created run ID. Failed owned auto-parent finalization
also attempts to mark that parent failed, never a pre-existing parent.

Artifact delivery is not transactional: earlier successful destinations retain
their files when a later one fails. The error identifies both; NexuML does not
delete prior uploads or retry silently. Use `logging=None` or no selected backends
to intentionally disable tracking.

## Private monitoring access

The banner suggests shell-quoted loopback-only commands: TensorBoard port 6007,
MLflow 5000, distinct from Viser 8080. Run them on the worker with the store and use
an approved private tunnel. These are suggestions, not started services/reserved
ports; select unused ports for concurrent jobs. HTTP(S) tracking uses the existing
service instead of another `mlflow ui`; the banner includes the actual run ID when
available. Do not expose credentials in logs or URLs.

On KubeRay, metrics already occupies 8080: explicitly choose Viser 8081 and use
the [private worker forwarding route](/how-to/isaac-read-only-viser/#kuberay-worker-access).
This does not change the standalone viewer's generic default or start a UI service.

## Diagrams and no external logger

`LoggingSpec.diagram` controls Mermaid export independently of scalar loggers. See
[pipeline diagrams](/explanation/diagrams/). `ScenarioSpec.logging=None` disables
configured NexuML loggers. Plain `LoggingSpec()` has no TensorBoard/MLflow/DVCLive backend,
though its diagram configuration is enabled by default. The base library's
`default_logging()` intentionally selects separate convenience defaults.

Relative paths use `NEXUML_LOGS_ROOT` where the relevant NexuML helper applies;
absolute/remote paths follow their backend rules. See [exact root rules](/reference/environment/)
instead of assuming one shared output tree. Checkpoint callbacks have their own path
settings. Next, add [checkpoint policy](/how-to/checkpoints/) or [Optuna tracking](/how-to/tune/).

title: Evaluate a model
description: Distinguish pipeline metrics, post-train fitted model state, and reporting algorithms.
---

**Goal:** evaluate trusted exported models or complete policies without training.
The package selects the model/test-split or policy/environment path:

```bash
nexuml evaluate /approved/export
nexuml evaluate /approved/export --scenario-file experiment.py
```

Models use the packaged computation, fitted state, dataset test split and existing
Lightning test hooks. Policies run episodes without creating a learner. Neither
path creates an optimizer or replaces the exported architecture/weights. Raw weights
without a complete model definition are insufficient. Packages and Python files
are trusted executable local code, not a sandbox.

The same `scenario() -> ScenarioSpec` file contract is used for training and
evaluation. It supplies model data/evaluation/logging, or policy evaluation
environment, optional `policy_evaluation` and logging. The selected environment is
`interaction.evaluation_environment` when supplied, otherwise `interaction.environment`.
Without the flag, embedded package definitions are used.

Existing `test` assignments are respected. Sources without split metadata use the
existing seeded data-module split; rebuilding cannot recover unrecorded random
partitions. An empty test split fails instead of borrowing train/validation data.
Cached preprocessing must already exist; evaluation does not rebuild or overwrite
it, and never fits pipeline components on the test split.

## Overrides and device placement

```bash
nexuml evaluate /approved/model -O data.loader.batch_size=128
nexuml evaluate /approved/model -O evaluation.test_result_metrics=all
nexuml evaluate /approved/policy --device cuda:0 \
  -O training.evaluation.episodes=20 -O training.evaluation.seed=123
```

Model overrides are limited to `data`, `evaluation` and `logging`. Policy overrides
use `policy_evaluation` or `training.evaluation`, logging and
`interaction.evaluation_environment`; do not mix the evaluation namespaces. Native
recipes may save zero in-fit episodes: request standalone episodes explicitly.
Both paths default to CPU; `--device` selects evaluation placement without changing
the saved training device. See [policy replay](/how-to/reinforcement-learning/).

Evaluation also remains part of `nexuml train`; the following sections describe
the same model components used by standalone testing.

## Pipeline losses and metrics

Layers emit named values such as `classification_loss`, `accuracy`, or `f1`.
`TrainingSpec.loss_keys` selects/weights losses; `metric_keys` selects emitted pipeline
metrics to log in train/validation/test. Merely naming a metric does not create it.

## Post-train fitted pipeline layers

Some score-producing layers require the completed training set after gradient training.
They use `PostTrainFitLayer`. Local execution runs:

```text
fit → validate → fit each unfitted PostTrainFitLayer over the training loader → test
```

Their fitted state produces model outputs, such as anomaly scores, during test.
Reporting/analysis is instead an evaluation-algorithm concern.

## Configure a reporting algorithm

For a scenario already producing `anomaly_score` with binary labels under `y_true`:

```python
from nexuml.core.types import EvalAlgorithmSpec, EvaluationSpec
from nexuml_library.evaluation.anomalous_sound_detection.asd_evaluator import AnomalyEvaluator

evaluation = EvaluationSpec(
    algorithms=[EvalAlgorithmSpec(
        algorithm=AnomalyEvaluator(score_key="anomaly_score", max_fpr=0.1),
        label_key="y_true",
    )],
    test_result_metrics=["auc", "pauc"],
)
```

Attach this section to that scenario and run:

```bash
nexuml train my-anomaly-scenario
```

This is not a replacement evaluation for the synthetic reconstruction example, which
does not emit anomaly scores/labels. Validate the dataset population and label semantics
before interpreting AUC.

During test NexuML runs the pipeline, attaches declared/available evaluation metadata,
calls each algorithm's `eval_batch(x, y)`, then `eval_end()`, `visualize(logger)`, and
`results()`. Immutable semantic settings belong to the definition; accumulators belong
to its private runtime.

`EvalAlgorithmSpec` owns `name`, `enabled`, axis keys, `feature_key`, and `label_key`.
`EvaluationSpec.test_result_metrics` chooses which returned scalars appear in test results:
`"none"`, `"all"`, or a list. For the example, inspect `auc`/`pauc` in test results.
Visualizations/files depend on configured [loggers](/how-to/tracking/); none are implied
by naming a result alone.

Ray rejects stateful `evaluation.algorithms` because independent worker accumulators
would change their meaning. Keep these scenarios local; see
[distributed restrictions](/how-to/training-backends/ray/#distributed-semantic-restrictions).

Next, [add a custom algorithm](/how-to/custom-eval-algorithm/) or use a real emitted
metric for [tuning](/how-to/tune/). Research selection must use validation/research data,
not feedback from a held-out final test set.
